## Version 2.5.1

### Security

- **Publishing a Skill now requires an admin (#225, #238)** — any Desk User could previously create an `FAC Skill` as Published + Public with no server-side check. Skills carry agent instructions rather than passive data, so that let a low-privileged user's content steer an agent running under someone else's permissions. Publishing and Shared/Public visibility now require **Assistant Admin** or **System Manager**, enforced in the DocType controller so the rule applies to the Desk form, the FAC Admin page, and the REST API alike. The default visibility for new skills changed from Public to Private. Existing skills are not modified; a one-time patch logs any pre-existing non-admin-published skill for manual review.
- **Private skills no longer leak into other users' tool descriptions (#225, #238)** — with Skill Mode set to `replace`, the tool → skill map was built without any visibility check, so a Private skill could replace a tool's description for users who could not read it. The map is now scoped to the requesting user, and when several accessible skills target the same tool the winner is deterministic: app-shipped system skills first, then most recently modified.
- **An admin's publish decision now covers the content it approves (#239, #240)** — the check above guarded the status/visibility transition only, so after an admin published a reviewed draft its owner could still rewrite the content, repoint it at a different tool, or widen its shared roles without further review. While a skill is Published and Shared/Public, only an admin can change its title, description, content, linked tool, or shared roles. Owners can still take their own skill out of circulation at any time — set it back to Draft, edit, and ask an admin to re-publish. Non-admins can also no longer mark a skill as a system skill.

### Fixes

- **`list_documents` returns submitted documents by default (#227, #231)** — on submittable DocTypes the tool returned drafts and cancelled records alongside submitted ones, so totals and lists silently included documents that do not count. It now applies `docstatus=1` when the caller has not asked for a specific status, and says so in the response. Pass `docstatus` explicitly to include drafts or cancelled documents.
- **Near-miss Link filters are explained instead of returning nothing (#228, #232)** — filtering on a Link field by a value that does not exist returned an empty result with no indication that the value itself was the problem. A zero-row response now carries an `unresolved_filters` key naming the unmatched value and suggesting close matches the user can actually see.
- **Report filters are validated against the report's own contract (#229, #233)** — `report_requirements` advertised filter defaults that `generate_report` then rejected, because the accepted values were hardcoded per filter name rather than read from the report. Both tools now derive options and defaults from the report's own filter definitions, so what is advertised is what is accepted, and rejections come back with structured `error_details` rather than a bare message.
- **Filter discovery runs for every report type (#223, #224)** — discovery was attempted only for Script Reports. Every other type fell through to name-pattern guidance with no diagnostics, which a caller cannot distinguish from a report that genuinely takes no filters. Discovery now runs for all types, Custom Reports dereference their reference report, and every response carries `filter_discovery_status`.
- **Programmatically shared report filters are discovered (#221)** — filters built by a shared helper rather than declared as a literal array are now resolved.
- **`run_python_code` honours `return_variables` as a filter (#237)** — the argument was additive: requesting two variables returned those two plus every other user-defined global, bloating responses. When `return_variables` is set, only those names are serialized. Omit it for the previous behaviour of returning everything.

### Documentation

- **Schema access is documented as live (#230, #234)** — FAC reads DocType metadata from Frappe at the moment a tool is called and keeps no schema copy: no snapshot table, no embedded index, no sync command to re-run. Custom DocTypes, Custom Fields, and Property Setters are visible on the next tool call, and permissions are evaluated per call. The previous internals documentation implied metadata and permission results were cached, which was the likely source of the misconception. If you reach FAC through another product that embeds it, that layer may keep its own cache.
- **The Skills guide matches the new permission model** — a new "Who can publish or share a skill?" section covers what non-admins can and cannot do and the draft → review → publish flow, and the guide now notes that the `replace` mode map is per user. One upgrade note: a Published + **Private** skill used to drive tool-description replacement for everyone and now drives it only for its owner. Make it Public or Shared if it was meant to apply site-wide.
